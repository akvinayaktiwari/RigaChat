# Design: Journey Observability — the operator's executions console

Resolves **Open Question #10**, deferred in the 2026-07-26 journeys design and
again in the 2026-07-29 builder-UX addendum ("client-visible 'where is my lead
right now' timeline view — still undesigned"). This session reframes it: the
reader is the **operator**, not the client.

## Problem Statement

There is no way to answer "which journeys are running, and are they working"
from inside the product. The journey engine writes rich events, but they are
only readable one lead at a time. Answering an operational question today means
opening the AWS console.

The proof is this session: the founder asked which journey was active on his own
account, and the only way to answer was `aws dynamodb scan` against three
tables. If the person who built the system cannot answer that from the product,
no client ever will.

## Demand Evidence

Weak on the client side, strong on the operator side. Nobody is paying for this
and no client has asked for it. What is real:

- The founder hit the failure himself, live, mid-session, on his own data.
- Status quo answer: "I open CloudWatch / DynamoDB by hand."
- 23 bots across 5 clients, all operated by one person. Every added client makes
  a manual console trip more expensive.

Deliberately recorded: this is **operator pain, not customer demand**. It is
worth building because it is cheap and it unblocks operating the product, not
because a customer is asking. If that distinction stops being true — a client
asks "did your bot message my lead?" — the priority goes up, not the design.

## Status Quo

`aws logs tail` and `aws dynamodb query` by hand. Answers "what happened to this
one lead" after some effort. Never answers "is the journey working."

## Target User & Narrowest Wedge

**User:** the founder, operating 23 bots on behalf of 5 clients. Confirmed, not
assumed: every journey in production belongs to his own Cognito account. No
client has ever created one.

**Wedge:** a terminal event plus a per-journey executions feed, plus a cross-bot
"what is live right now" index. Explicitly not a funnel dashboard.

## Constraints

- Single Lambda, Hono, DynamoDB. No new datastore.
- Lambda env is at 3597/4096 bytes. **No new environment variable.** Table names
  live in `lib/table-names.ts`.
- Architecture rules are immutable: routes -> services -> repositories.
- Volume is tiny (240 events, 26 executions). Any design that only works at
  scale is over-built; any design that breaks at 100x is under-built.

## Premises

1. **Operator-first.** Cross-bot is the default view; a per-bot dropdown is the
   wrong primary axis. Dense and technical beats friendly — stepIds and tool
   names are features here, not leaks.
2. **No new storage.** `lead_events` already carries every journey event with
   `bundleId` and `stepId`. This is an index plus a read path.
3. **The terminal event must be written, with an outcome.** `journey_ended` is
   declared at `types/index.ts:147` with zero call sites. *Revised after the
   Codex cold read:* a bare "ended" is not enough — it must carry
   `completed | failed | cancelled | timed_out`, the final `stepId`, an error
   summary, and the execution ARN. Otherwise a healthy finish and a crash still
   look identical.
4. **No funnel percentages yet.** At 26 executions every rate is noise, and a
   chart that looks authoritative while being noise is worse than no chart.

## Cross-Model Perspective

Codex, cold read, no access to the conversation:

- **Steelman:** "an operator-grade execution console for journeys: a cross-bot,
  searchable record of every lead's journey run, its current step, and its
  outcome. It turns 'did this automation work?' from a CloudWatch/DynamoDB
  investigation into a fast operational workflow."
- **Most revealing answer:** it independently picked the same quote — *"No, I
  set up every journey myself"* — and drew the same conclusion: optimise for
  dense execution debugging, not client-friendly dashboards.
- **Challenged premise 3**, correctly. Adopted; see above.
- **Disagreement, kept:** Codex said skip "cross-journey dashboards." A funnel
  dashboard, yes. But the cross-bot summary strip stays — it is one line per
  live journey, and it is the fix for the discoverability failure that started
  this thread. Codex under-weighted that because the summary it was given
  emphasised debugging over discovery.

## Approaches Considered

### Approach A: Index + derive on read — CHOSEN
GSI on `bundleId`, terminal event, endpoint groups events by lead and reduces to
a status. Effort M, risk Low.

### Approach B: Materialised execution read model
Extend `journey_executions` into a per-run summary row updated as events append.
O(1) status, scales indefinitely. **Rejected for now:** a second store that can
disagree with `lead_events`, and this codebase spent three fix cycles on exactly
that class of bug the same morning. A is upgradeable to B behind the same API.

### Approach C: Terminal event + CLI, no executions UI
Ship `scripts/journeys.sh`. **Rejected:** honest about current behaviour but
dies the moment anyone else operates the system, and can never be shown to a
client.

## Recommended Approach

**A.** At 240 events the reduce is free, it adds no write to the hot journey
path, and events stay the single source of truth.

### What gets built

1. **Write the terminal event.** `journey_ended` with `outcome`, final `stepId`,
   `error`, `executionArn`. Must fire on the failure path too — a Step Functions
   `Catch` that reaches the executor, not only the happy path. This is the part
   most likely to be got wrong: an event written only on success recreates the
   exact ambiguity it exists to remove.
2. **GSI `bundleId-ts` on `lead_events`.** Sparse — only journey events carry
   `bundleId`, so non-journey rows stay out of the index.
3. **`GET /api/journeys/:botId/:bundleId/executions`** — paginated, newest
   first, grouped by `leadId`, status derived from the latest event. Route ->
   service -> repository, no layer skipping.
4. **`GET /api/journeys/active`** — the cross-bot index. Reads
   `journey_trigger_claims` for the caller, which is already the authoritative
   answer to "what is live" and a point read per claim.
5. **Executions tab** on the journey detail page, and an **"Active across all
   bots"** strip at the top of the Journeys page, linking into each journey.
6. **Default the bot dropdown** to a bot that has a live journey instead of the
   alphabetically first one.

### Failure modes to design against

- A journey with no terminal events at all (all pre-existing runs) must render
  as "unknown", never as "running forever".
- The 26 existing executions predate the terminal event. No backfill: label them
  `unknown` rather than inventing an outcome.
- An execution whose Step Functions run was deleted (see the delete caveat in
  `journey-service.ts`) has events but no live execution. Show last known state.

## Open Questions

1. Should `journey_ended` also fire when a journey is **paused** while leads are
   mid-flight? Current answer: no — those executions genuinely keep running, and
   a terminal event would lie. Revisit if the feed makes paused-but-running
   confusing.
2. Retention. `lead_events` has no TTL by design (it is the audit record). The
   executions reduce gets slower forever. Fine at this volume; needs a bound
   before a client with real traffic.
3. Does the client ever see this? Out of scope today, but the endpoint is
   already clientId-scoped, so a client-facing view is a later layer over the
   same API rather than a rewrite.

## Success Criteria

- "Which journeys are live?" answerable in one page load, without a dropdown.
- "Did this journey do anything in the last 24h?" answerable without the AWS
  console.
- A failed tool call is visible in the dashboard within one refresh.
- Zero `aws dynamodb scan` invocations needed to answer either question.

## Dependencies

- No new env var (Lambda env at 3597/4096).
- GSI creation on `lead_events` — a provisioning script, matching the existing
  `scripts/provision-lead-events.sh` pattern.
- Two open P1 race findings in TODOS.md touch the same transition code. Not
  blocking, but the terminal-event write lands in `journey-executor-service.ts`,
  near them.

## The Assignment

Before writing any of this: **take the one live journey and deliberately break
it.** Point its booking tool at a bad endpoint, send a test lead through, and
time how long it takes you to find out what went wrong using only what exists
today. Write down the number and what you actually opened to get the answer.

That number is the thing this design has to beat, and right now nobody has
measured it — including you. If it turns out to be two minutes, build Approach C
and move on.

## What I noticed about how you think

- You asked "should there be some logs of the journey part?" — and the answer
  was that you had already built them, a month ago, and forgotten. Five event
  types, `bundleId` on every row. The instinct to instrument was right the first
  time; what got skipped was the read path. That is a pattern worth watching:
  you build the write and move on.
- `journey_ended` is declared in the type union and never written. That is the
  same shape as the `MessageChannel` interface in your own CLAUDE.md — declared,
  zero implementations. You write the type when you see the design, then ship
  the part that runs. The types are load-bearing documentation of intent; the
  gap between them and the call sites is where your real backlog lives.
- You answered "No, I set up every journey myself" without hedging. A lot of
  founders would have said "well, clients *can*." That one word decided the
  whole design.

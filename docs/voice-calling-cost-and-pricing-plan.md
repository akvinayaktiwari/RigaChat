Compiled 3 September 2026. FX used: ₹94.5/$1 (live mid-market rate, up from the ₹88 assumed in the earlier draft — the rupee has weakened ~7% since that draft was written, which pushes every USD-denominated line item up by the same amount).

This document does not re-litigate the engineering plan (Phases 0–5, the `VoiceProvider` seam, the regulatory gaps) — that analysis holds up. What it does is replace every "≈" and "unverified" pricing line with a number I could actually source, show you the arithmetic so you can re-run it with your own call statistics, and turn that into a customer price list. ## 1. What changed since the last draft

Two things move the whole model, in opposite directions:

1. **The rupee is weaker.** ₹94.5/$1 vs. the ₹88 assumed earlier. Every dollar-denominated cost (OpenAI, Twilio) is ~7% higher in rupee terms than previously estimated.
2. **Telephony is far cheaper than the earlier draft assumed.** The earlier draft priced the telephony leg using Twilio's India rate (~₹4.4–6.6/min) as a stand-in because it couldn't find a real number for the recommended provider (Exotel). I found one: **Plivo publishes ₹0.38/min flat for Indian domestic calls, in and out, with audio streaming included at no extra charge, and ₹200/month per number.** That is roughly a tenth of what the earlier model used for the telephony line. This alone cuts 2–4 rupees off every blended per-minute figure below.

Exotel itself still doesn't publish per-minute rates anywhere I could find — pricing is sales-gated and appears to run on a prepaid-credit model. Independent comparisons put it at 10–25% above Plivo, so ₹0.42–0.48/min is a reasonable planning number until you get a real quote.

## 2. AI engine cost — sourced, with the arithmetic shown

### 2.1 OpenAI Realtime — current model is `gpt-realtime-2.1`

The model referenced in the earlier draft (`gpt-realtime`) has been superseded; the current flagship is **`gpt-realtime-2.1`**, with a **`gpt-realtime-2.1-mini`** tier. Pricing per OpenAI's published rate card:

| Rate (per 1M tokens) | gpt-realtime-2.1 | gpt-realtime-2.1-mini |
|---|---:|---:|
| Audio input | $32.00 | $10.00 |
| Audio input, cached | $0.40 | $0.30 |
| Audio output | $64.00 | $20.00 |
| Text input | $4.00 | $0.60 |
| Text output | $24.00 | $2.40 |

Billing mechanics that matter for the math: **1 token per 100ms of input audio, 1 token per 50ms of output audio** — so a full minute of audio *sent to* the model is 600 tokens, a full minute of audio *generated by* the model is 1,200 tokens.

Worked per-minute cost, assuming the caller's mic streams for the whole call (input runs 100% of the minute) and the agent talks for 50% of the minute — the same talk-ratio assumption the earlier draft used, so the two are comparable:

| | gpt-realtime-2.1 | gpt-realtime-2.1-mini |
|---|---:|---:|
| Input (600 tok, uncached) | $0.0192 | $0.0060 |
| Output (600 tok = 50% of 1,200) | $0.0384 | $0.0120 |
| **Uncached total /min** | **$0.0576 → ₹5.44** | **$0.0180 → ₹1.70** |
| Input if 70% cache hit* | $0.0059 | $0.0019 |
| **Steady-state (cached) /min** | **$0.0443 → ₹4.19** | **$0.0139 → ₹1.31** |

*OpenAI's Realtime API automatically caches repeated prefix context (the growing conversation history) at a 98–99% discount. In a multi-turn call this mostly reduces the **input** side — it does not touch output cost, because the agent's speech is freshly generated every turn and can't be served from cache unless it's a byte-for-byte repeat (see §4). Treat "uncached" as your cost on short calls (1–2 turns) and "steady-state" as the floor on longer ones. This is a model, not a measurement — the real number depends on how much of your context OpenAI actually caches turn to turn, which you can only get from your own token logs (you already meter this — `voice_call_logs` should tell you the real cache-hit rate after a week of traffic).

### 2.2 Sarvam — the model names have moved too

Saarika and Sarvam-M, named in the earlier draft, are now listed as **deprecated** on Sarvam's own pricing page. The current lineup:

| Component | Model | Price |
|---|---|---:|
| STT (real-time/streaming) | Saaras v3 | ₹30 / hour = ₹0.50/min |
| TTS (real-time/streaming) | Bulbul v3 | ₹30 / 10,000 characters |
| LLM | GLM 5.2 | ₹128.10 / ₹23.79 (cached) / ₹402.60 per 1M tokens (in/cached-in/out) |
| LLM (cheaper tier) | Sarvam 105B | ₹29.28 / ₹10.98 / ₹73.20 per 1M tokens |

Sarvam still publishes **no end-to-end turn-latency number** — same gap the earlier draft flagged, and it's still true. Streaming STT/TTS only shipped in August 2026, so there is no track record yet either.

Worked per-minute cost, same talk-ratio assumption (agent speaks ~100 words/min when talking, 50% of the call), ~5.5 characters per English word:

- STT: continuous for the full minute → ₹0.50
- TTS: 50 words × 5.5 chars = 275 characters of agent speech per minute-of-call → 275/10,000 × ₹30 = **₹0.83**
- LLM (GLM 5.2, ~300 input + 100 output tokens/min, a rough conversational-turn estimate): ₹0.038 + ₹0.040 = **₹0.08** (with cached context: ~₹0.05)

**Sarvam cascade total: ≈ ₹1.35–1.40/min.** This is markedly cheaper than the earlier draft's ₹2.9/min estimate — but that's an artifact of assumptions (words/min, characters/word, turns/min) that neither draft has measured against real calls. Treat both numbers as directional. **Hindi and code-switched Hinglish will use more characters per spoken word than this English-based estimate**, so budget 15–25% higher for Sarvam's TTS line on real Hindi-heavy traffic.

## 4. Caching architecture — where the real savings are

The token-level "cached input" discount in §2.1 is real but small in absolute terms (it only touches the input side, and input is the cheaper of the two audio legs). The caching that actually moves your cost per minute lives one layer up, in your own application:

**1. Canned-response TTS caching (biggest lever, Sarvam and any TTS-based stack).**
A large fraction of what a sales/support voice agent says is not novel — greetings, "let me check that for you," pricing-plan recitations, business-hours statements, disclosure/consent scripts (which TRAI may make mandatory verbatim text, see the original plan's §5). Pre-synthesize these once, store the audio (S3, keyed by text hash + voice + language), and play the cached clip instead of calling Bulbul/ElevenLabs/OpenAI TTS again. This is a 100% cost cut on every cache hit, not a discount — and it also removes TTS's first-audio latency from the turn entirely, which helps the latency budget in the original plan's §2 more than any model swap would. Implement this in `voice-relay` as a lookup keyed on `hash(text + voice_id + lang)` before any TTS call, invalidated whenever a script/prompt changes.

**2. Semantic response caching for the LLM turn.**
For the ~20–30% of turns that are FAQ-shaped ("what are your office hours," "do you have a 2BHK," "what's the price of the Growth plan") a vector-similarity lookup against a small cache of (question-embedding → answer) pairs can short-circuit the LLM call entirely, using the embedding pipeline you already run for RAG (Pinecone, `text-embedding-3-small`). Set a high similarity threshold (0.92+) to avoid answering the wrong question confidently — a wrong cached answer is worse than a slow correct one. This saves the LLM-token cost and, more importantly, saves the LLM's turn-taking latency, which is the term that dominates your latency budget after endpointing.

**3. RAG context caching (works with OpenAI's native prompt caching).**
Your `search_knowledge_base` tool result for a given bot rarely changes within a call, and often not across calls on the same day. If you structure the system prompt so the retrieved KB chunks sit in a stable prefix (bot-scoped, not per-question), OpenAI's automatic caching (§2.1) and Sarvam's cached-input LLM rate both apply to it — turning a ₹128/1M-token line into a ₹24/1M-token line for the part of the prompt that doesn't change turn to turn.

**4. What caching cannot do.**
It cannot reduce audio-output cost for genuinely novel speech, and it cannot reduce the STT or telephony legs at all — those are billed on raw audio duration regardless of what's being said. This is worth saying plainly to the client: caching buys you 15–35% off the AI-compute line depending on how repetitive their call scripts are, not a blanket discount on the whole per-minute cost. Telephony and STT floor the savings.

**Recommended build order inside Phase 5** (the "Sarvam lane and hardening" phase in the original plan): TTS caching first (cheapest to build, immediate win, no correctness risk), semantic FAQ caching second (needs a confidence threshold tuned against real call transcripts before it's safe), prompt-prefix caching third (mostly free once your prompt is structured to keep the RAG context in a stable position).

## 5. What the market actually charges — and what to charge

### 5.1 The India voice-AI pricing landscape

Published and third-party-aggregated per-minute rates for AI voice agents sold to Indian businesses, current as of Sep 2026:

| Tier | Price to end customer | What it typically includes |
|---|---:|---|
| Entry / IVR-replacement | ₹2–6/min | Basic NLU, limited language support, platform fee often added separately (₹15,000–₹2,00,000/month) |
| Mid-market conversational | ₹3–6/min | Full conversational AI, single language, CRM integration variable |
| Premium (Hindi/regional NLU + CRM) | ₹9–12/min | Real Hindi/Hinglish handling, sentiment detection, native CRM |

Platform-orchestrator pricing (Vapi, Retell — the "don't buy this" category from the original plan, confirmed):
- **Vapi:** $0.05/min platform fee, *on top of* STT/LLM/TTS charged at cost or bring-your-own-key
- **Retell:** no flat fee, but $0.07–0.31/min all-in once you sum their voice infra ($0.055) + TTS ($0.015–0.04) + LLM ($0.045–0.16) + telephony ($0.015) + add-ons

Both confirm the original plan's read: a third-party orchestrator's all-in cost lands close to or above what you'd charge a customer, before you've added your own margin. Building on your own relay, with the real provider costs from §2, is the only way to have room for a margin.

### 5.2 Recommended pricing for Vyostra AI

Your existing plan structure (Starter ₹1,999 / Growth ₹5,499 / Agency ₹14,999, monthly minute allowances) is the right shape to extend, not replace. Two decisions this document can now ground in real numbers:

**Which engine to bundle by default.** Your cheapest credible stack (Sarvam cascade + Plivo, ≈₹1.75/min all-in, or gpt-realtime-2.1-mini + Plivo at ≈₹1.7–2.1/min) should be the *included* engine in every plan. Reserve gpt-realtime-2.1 flagship (₹4.6–5.8/min all-in) as a named add-on for clients who specifically need English-first, lowest-latency handling — price it separately rather than blending it into a flat allowance, because its cost is 2.5–3x the base stack.

**Per-minute pricing, worked from cost:**

| Plan | Included voice minutes/month | Cost basis | Suggested included-minute price to client | Overage rate |
|---|---:|---|---:|---:|
| Starter | 150 min | Sarvam/mini stack, ≈₹1.8/min cost | Bundle at ₹350–450/month (≈₹2.3–3/min effective) | ₹4/min |
| Growth | 750 min | Sarvam/mini stack | Bundle at ₹1,800–2,400/month (≈₹2.4–3.2/min effective) | ₹3.5/min |
| Agency | 3,000 min pooled | Sarvam/mini stack, negotiate Plivo volume rate | Bundle at ₹6,500–8,500/month | ₹3/min |
| Flagship add-on (any plan) | — | gpt-realtime-2.1, ≈₹5/min cost | — | ₹9/min flat |

This prices your base offering inside the "mid-market conversational" band (₹3–6/min effective) the market already accepts, keeps 40–60% gross margin on the AI-compute + telephony cost once you account for your own infra and support overhead, and prices the flagship engine at the low end of the "premium" band (₹9–12/min) where the market has already shown willingness to pay for lower latency and English quality. Whether ₹1,500–1,800/month of cost per client (the original plan's own back-of-envelope for a 300-minute entitlement) is a margin or a hole is answered directly by this table: at ₹1.8/min cost, 300 minutes costs you ≈₹540, not ₹1,500–1,800 — the earlier estimate was using the Twilio-proxied telephony cost, which this document replaces.

## 6. What still needs a phone call, not more research

Unchanged from the original plan, and still true after this pass:

1. **Exotel and Plivo sales calls** — real committed per-minute rates at your expected volume, DID setup fees, concurrency limits, and (for Exotel specifically) whether AgentStream's 10-second bot-response timeout and 60-minute session cap fit an enterprise sales call.
2. **Sarvam sales call** — a measured end-to-end turn-latency number on your own call audio, not their component-level VAD figure. Nothing in this document changes the original plan's instruction: do not put an SLA behind Sarvam until you've measured it yourself.
3. **The AI-disclosure clause** — I re-checked this and could not find it in any primary source either. One law firm's TCCCPR amendment summary (Saikrishna & Associates) explicitly describes AI-telemarketing disclosure rules as something **TRAI is "considering," not something enacted** as of the amendments reviewed. Treat the original plan's caution as *more* warranted, not less: get counsel to confirm current status before writing the greeting-script requirement into the product, and don't assume it's live.
4. **DPDP penalty ceiling** — confirmed the Rules were notified 17 November 2025 (matches the original plan). The ₹250 crore figure is the Act's statutory ceiling for the "reasonable security safeguards" violation category; other violation categories carry lower ceilings (₹200 crore appears for breach-notification failures in some summaries). Have counsel confirm which ceiling applies to voice-recording mishandling specifically — it's not automatically the largest number.

None of these four can be resolved by more search — they need either a vendor on the phone or a lawyer reading the gazette text.
